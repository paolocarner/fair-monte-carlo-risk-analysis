Thanks again @paolocarner — this went deeper than the original comment, and it's fixed properly now rather than patched around.

**What was wrong**, in full: TEF was collected directly as its own distribution, which is a legitimate way to estimate it per the O-RT Standard (Appendix A.1 explicitly allows estimating at the TEF layer rather than decomposing into Contact Frequency and Probability of Action). But the "Vulnerability" section separately asked for a **second** "Contact Frequency (%)", multiplied it by Probability of Action and a Vulnerability Rate, and multiplied *that* back into the already-complete TEF — double-counting contact and action, and mislabeling Contact Frequency as a percentage when O-RT §2.4 defines it as a count of contacts/year.

**What's fixed:**
- Contact Frequency is now a real min/mode/max **count** input (contacts/year), not a percentage.
- Threat Event Frequency is *actually computed* as `TEF = Contact Frequency × Probability of Action` (O-RT §4.3.1) via a new `derive_tef_from_contact()` function — not just described in a caption next to two unrelated numbers.
- Vulnerability is a single, directly-set probability applied to that derived TEF (O-RT §4.3.2) — never re-multiplied by Contact Frequency or Probability of Action.
- The sensitivity ("tornado chart") analysis now treats Contact Frequency and Probability of Action as two independent levers, since TEF is genuinely derived from them now.
- All 9 preset scenarios were recalibrated. Contact Frequency and Probability of Action were reverse-derived to reproduce the *same* previously-published TEF values (so TEF itself didn't change), but Vulnerability could not simply be carried over — doing so, now that it's no longer double-discounted, implied absurd outcomes (e.g. ~130 successful ransomware compromises/year for one SMB). Vulnerability was independently recalibrated against plausible annual loss-event targets. Full derivation and caveats are in `PRESET_METHODOLOGY.md` — these are reasoned illustrative estimates, not sourced statistics, and should be validated against real client/control data before use in an engagement.
- The same bug existed in `custom_scenario_template.py` (the file the README points consultants to for per-client work) and in worked examples across `FAIR_Monte_Carlo_Guide.md`, `FAIR_Parameter_Reference.md`, `STATISTICS_FAQ.md`, `STATISTICS_QUICK_REFERENCE.md`, `UPDATING_STATISTICS_GUIDE.md`, and `DATA_FLOW_DIAGRAM.md` — all fixed to match.

**What this means for existing results:** if you've run assessments with previous versions, the corrected model will show meaningfully **lower** ALE for the same scenario, because the old model was silently crushing Loss Event Frequency via the double-count. That's the bug being fixed, not a new problem — but worth knowing before comparing an old report to a freshly-run one for the same client.

**Testing:** added a `derive_tef_from_contact()` unit test suite (including an empirical proof that scaling a PERT distribution's parameters by a constant is mathematically identical to scaling its samples, which is what makes deriving TEF from Contact Frequency this way valid), plus a new end-to-end suite (`tests/test_fair_dashboard.py`) using Streamlit's `AppTest` framework that actually runs the dashboard headlessly — preset loading, derived-TEF correctness, validation, all 9 presets executing cleanly, sensitivity-tab levers, and legacy config-file migration. 66 tests passing.
